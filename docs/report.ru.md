# Отчёт о лаборатории мониторинга и реагирования

Отчёт учебной лаборатории мониторинга и реагирования: установка сервисов, обработка журналов и тестовые сценарии. Версии указаны по записям настройки; исходные конфиги, программы и полные протоколы испытаний пока не включены в репозиторий.

Ограничения стенда: объединение событий по IP не подтверждает атаку. WAN-карантин ограничивает внешний маршрут и не является полной изоляцией. Ловушка с баннером не реализует SSH. TCP-правило с `!51820` не исключает UDP WireGuard; загрузка правила не подтверждает его срабатывание. Ранняя схема реакции по EVE/priority 1 отличается от более позднего обработчика fast.log. Эти ограничения подробно разобраны в английской документации.

Задача 3. Централизация логов (SIEM)
1. Развёртывание стека сбора логов
На VM2 развёрнут Grafana Loki. Loki выбран с учётом ограничения RAM (3.8 ГБ).
Что установлено:

Grafana Alloy версии 1.16.1, это агент сбора логов.  Лежит в /usr/local/bin/alloy, конфиг /etc/alloy/config.alloy. Запущен как systemd сервис alloy.service.
Grafana OSS поставил через APT репозиторий, слушает порт 3000. Доступ к ней через SSH туннель с локального компа (ssh -L 3000:localhost:3000 administrator@PUBLIC_ENDPOINT -p 2223), потому что GUI на сервере нет. Loki подключил как Data Source с URL http://localhost:3100.
2. Сбор логов из четырёх источников
Все источники собирает агент Alloy и приводит к единому полю src_ip, чтобы потом можно было коррелировать один IP по всем источникам. У каждого источника свой формат, поэтому парсинг разный:
Nginx (/var/log/nginx/access.log). Чтение файла, IP извлекается regexp ом из начала строки (там IP всегда первый).
ModSecurity (/var/log/modsec_audit.log). Нативный multipart формат (не JSON, JSON в этой сборке не завёлся). IP находится в секции A, формат строки: [дата] unique_id IP порт IP порт. Извлекается regexp ом.
Suricata (/var/log/suricata/eve.json). Чистый JSON, парсинг через LogQL оператор | json, поле src_ip берётся сразу.
MikroTik. Логи фаервола приходят по протоколу Syslog. На VM2 настроил rsyslog слушать UDP порт 514, фильтр :rawmsg, contains "firewall" пишет их в файл /var/log/mikrotik/firewall.log, откуда читает Alloy. На MikroTik создал logging action remotesyslog (target=remote, remote=192.168.3.254:514) и привязал к topic firewall. В UFW на VM2 открыл порт 514 только для IP MikroTik (ufw allow from 192.168.3.1 to any port 514 proto udp). Было две проблемы пока заработало: сначала UFW блокировал порт, потом права на папку /var/log/mikrotik оказались неподходящие (rsyslog работает от пользователя syslog, пришлось сделать chown).
3. Dashboard корреляции атакующих
В Grafana сделал дашборд Security Overview. Главная панель это сводная таблица, которая связывает один и тот же IP атакующего по всем фронтам. Реализована через 4 LogQL запроса (по одному на источник), которые объединяются трансформацией Merge по полю src_ip. Структура таблицы: ip | modsec | suricata | nginx | mikrotik. Одна строка это один IP, и сразу видно его активность во всех системах. Если IP присутствует и в modsec, и в suricata, и в nginx, значит атака идёт по всем направлениям сразу.
Дополнительные панели: общий счётчик событий (Stat), топ атакующих по ModSecurity, топ по Suricata (с исключением внутренней подсети 192.168.0.0/16, чтобы свой трафик не попадал в статистику), Nginx сканеры по количеству ответов 4xx (это детект перебора URL), и забаненные IP по логам MikroTik.
4. Telegram уведомление с корреляцией двух условий
Написал Python скрипт /usr/local/bin/correlation_alert.py, запустил как systemd сервис correlation-alert.service с автоперезапуском. Логика:
Каждые 60 секунд делает два запроса к Loki через HTTP API (/loki/api/v1/query).
Запрос 1. Какие IP заблокировал ModSecurity больше 5 раз за минуту (count_over_time(...[1m]) > 5).
Запрос 2. Какие IP Suricata зафиксировала как сканеры портов за минуту (фильтр по сигнатуре alert_signature=~"ET SCAN.*").
Дальше вычисляет пересечение множеств IP из обоих запросов (set(A) & set(B)), то есть берёт только те IP, которые присутствуют в обоих результатах.
Уведомление в Telegram отправляется ТОЛЬКО если один и тот же IP попал в оба условия одновременно. То есть ModSecurity заблокировал его больше 5 раз за минуту И ПРИ ЭТОМ Suricata засекла с него скан портов. Если выполнено только одно из двух, уведомления нет. Сделал защиту от повторов, cooldown 10 минут на один IP.
уведомления приходят довольно редко. Когда поменял окно с 1 минуты на 3 минуты, они начали приходить активно (потому что два события чаще попадают в одно окно). Но оставил 1 минуту как вы и просили. уведы в телеграмм канале могу вас туда добавить или нужно было сделать в ввиде бота?

## R2 — отчёт о задаче 4

```text
Задача 4. Скрытый канал и защита от Lateral Movement
1. Защищённый туннель WireGuard
Между VM1 и VM2 поднял WireGuard туннель для админского трафика. Поставил пакет wireguard на обе VM, сгенерировал пары ключей (приватный + публичный) на каждой машине командой wg genkey | tee privkey | wg pubkey > pubkey, потом обменялся публичными ключами крест накрест (в конфиг VM1 пишется публичный ключ VM2 и наоборот). Конфиги лежат в /etc/wireguard/wg0.conf.
VM1: адрес 10.10.10.1/24, в peer прописан публичный ключ VM2, Endpoint 192.168.3.254:51820, PersistentKeepalive 25.

VM2: адрес 10.10.10.2/24, в peer публичный ключ VM1, ListenPort 51820. Endpoint у VM2 нет, потому что она просто ждёт подключения, а инициатор это VM1.
Туннель поднял через wg-quick up wg0, в автозапуск добавил systemctl enable wg-quick@wg0 на обеих машинах. В UFW на VM2 открыл порт 51820/udp только для VM1 (ufw allow from 192.168.3.253 to any port 51820 proto udp). Сначала handshake не проходил, transfer был 0 B received, оказалось UFW резал порт. После разрешения заработало, latest handshake появился, transfer пошёл в обе стороны.
Туннельные адреса (10.77.0.x) это виртуальная сеть поверх реальной. Сам туннель устанавливается через реальный адрес 192.168.3.254 (Endpoint), а уже потом общение шифрованное идёт по 10.77.0.x.
Админский доступ к VM1 через туннель работает командой ssh -p 2222 administrator@10.10.10.1. Важно что порт 2222, потому что sshd на VM1 слушает именно 2222 (не 22). Туннель идёт по внутренней сети а не через ether1, поэтому доступ к VM1 сохраняется даже когда она в карантине и без интернета.
2. Забытый конфиг приманка
На VM1 в папке DVWA создал файл приманку /var/www/html/DVWA/db_backup.sql.config с фейковыми кредами. Раньше клал в /var/www/html/ (корень), но DVWA лежит в /var/www/html/DVWA/, поэтому переложил туда, где атакующий реально окажется. Формат сделал как у настоящего бэкап конфига, секции [client] и [ssh], чтобы выглядело правдоподобно. Внутри указан host 192.168.3.254, ssh_port 2222, фейковые учётки backup_svc и bkpadmin; значения паролей закрыты. Права 644 (rw-r--r--), чтобы пользователь www-data мог прочитать, потому что Apache на VM1 работает от www-data, и атакующий который пробил DVWA будет иметь эти же права.
3. Honeypot на VM2
Поднял лёгкий SSH honeypot, питоновский скрипт /usr/local/bin/honeypot.py. Слушает порт 2222 на 0.0.0.0, отдаёт фейковый SSH баннер (SSH-2.0-OpenSSH_8.9p1) чтобы выглядело как настоящий SSH, и логирует все подключения (IP и что прислали) в /var/log/honeypot.log. Запустил как systemd сервис honeypot.service с автозапуском. Любое подключение на 2222 это атака, потому что легитимно туда никто не ходит. В UFW порт 2222/tcp открыл только для VM1.
4. Своё правило Suricata
Написал кастомное правило в /var/lib/suricata/rules/local.rules:
alert tcp 192.168.3.253 any -> 192.168.3.254 !51820 (msg:"lateral movement vm1->vm2 isolate"; flow:to_server; sid:1000002; rev:1;)
Логика. Ловит трафик от VM1 (192.168.3.253) к VM2 (192.168.3.254) на любой порт КРОМЕ туннельного 51820 (знак ! это отрицание). flow:to_server нужен чтобы ловить только когда VM1 сама инициирует соединение, а не когда она отвечает на проксирование (иначе ловило бы легитимный ответный трафик от nginx). sid 1000002 это id правила, локальные правила нумеруют от 1000000. Файл подключил в /etc/suricata/suricata.yaml в секции rule-files (около строки 2152), добавил строку local.rules. Сам файл переложил в /var/lib/suricata/rules/ потому что это default-rule-path. Загрузилось без ошибок, в логах 2 rule files processed, 0 rules failed.
5. Автоматический карантин VM1
На MikroTik создал address-list quarantine и правило firewall на позиции 0 (выше всех остальных правил):
chain=forward action=drop src-address-list=quarantine out-interface=ether1 log=yes log-prefix="QUARANTINE:"
Это правило дропает трафик от карантинных адресов только в интернет (out-interface=ether1 это WAN). Внутреннюю сеть не трогает, поэтому туннель и проксирование продолжают работать. place-before=0 чтобы правило стояло первым и срабатывало раньше всех accept.
Дополнил скрипт suricata-block.py. Добавил второй поток через threading, который параллельно мониторит /var/log/honeypot.log. Старую логику банов не трогал чтобы её не сломать, просто добавил рядом новую функцию quarantine_vm1() и новый монитор monitor_honeypot(). В main запускаются оба потока, monitor() для обычных банов по fast.log и monitor_honeypot() для карантина. Когда в honeypot.log появляется строка [ALERT] Подключение, скрипт через SSH (по ключу /home/administrator/.ssh/router_automation_key, юзер user) добавляет VM1 (192.168.3.253) в address-list quarantine на MikroTik, и VM1 теряет интернет. Защита от повторов через флаг файл /tmp/vm1-quarantined.flag, чтобы не слать команду по сто раз. Ещё добавил в tail флаг -n 0 чтобы скрипт читал только новые строки логов, а не реагировал на старые записи при рестарте.
Проверил всю цепочку целиком. На VM1 прочитал приманку через cat, потом подключился к honeypot на VM2 через nc 192.168.3.254 2222, honeypot записал обращение в лог, скрипт это увидел и сам кинул VM1 в карантин. На VM1 пропал интернет (ping 8.8.8.8 не идёт), но внутренняя сеть осталась (ping 192.168.3.254 работает). В логах suricata-block видно что оба механизма работают одновременно, и карантин VM1 по honeypot, и обычный бан внешних атакующих по fast.log (например в тот же момент забанился EXTERNAL_SOURCE_IP по сигнатуре ET CINS).
Чтобы вернуть VM1 в строй, надо убрать её из quarantine на MikroTik (/ip firewall address-list remove [find list=quarantine]) и удалить флаг файл на VM2 (rm /tmp/vm1-quarantined.flag).
6.Правило Suricata не получится сделать
Правило написал и загрузил правильно, но в текущей сети оно не триггерится. Разобрался почему. VM1 (192.168.3.253) и VM2 (192.168.3.254) сидят в одной подсети 192.168.3.0/24 на одном интерфейсе ether3 MikroTik, за виртуальным свитчом гипервизора. Трафик между ними коммутируется прямо на свитче и НЕ проходит через MikroTik. Проверил через traceroute (1 hop, то есть напрямую) и ip neigh (VM2 знает MAC адрес VM1 напрямую). А зеркалирование TZSP настроено на ether3 MikroTik, поэтому внутренний трафик VM1 VM2 в зеркало не попадает и Suricata его не видит. В eve.json трафика VM1 на VM2 нет вообще, только внешний.
Чтобы правило заработало, надо либо разнести VM1 и VM2 по разным подсетям (тогда трафик пойдёт через MikroTik и зеркалится), либо доступ к гипервизору чтобы настроить зеркало на виртуальном свитче. Доступа к гипервизору нет, дали только MikroTik и две VM. Поэтому детект обращения к ловушке сделал через лог honeypot, в этой топологии так работает надёжно и закрывает требование что при обращении к honeypot надо изолировать VM1.
Минус такого варианта в том что honeypot ловит только порт 2222, а правило Suricata ловило бы любой порт.
```
